# Option A — Chat rail

One chat is one contiguous timeline. Main runs are nodes down a quiet vertical rail, oldest first. Completed main runs become short two-line summaries; the current main keeps its full card and note preview. Children sit below their actual parent with inset cards, branch connectors, and a Child label. Compact mode preserves exactly this order, one bar per task, short completion bars, a small chat delimiter, and unmistakably inset child bars. Color is supplementary; geometry and text carry the distinction. See `mockup.html`.

The mockup shows two completed main runs, their active followup, two parallel children of that followup, and a separate chat in the same project. It uses 350/200 px expanded/compact widths matching the current presentation targets. A project label alone must never group chats. No aggregate progress: heterogeneous child estimates cannot be averaged honestly.

## Order and identity

- Group by the existing full `t3Thread` pair (environmentId, threadId). Unlinked tasks remain independent rows. Forks retain their own chat key.
- Maintain a stable group order by first observed creation time, ascending, with deterministic tie-breaking. Progress, completion, recall, and background updates never promote a group. Unrelated chats remain outside the rail. The cost is that newest active work is not necessarily the first group.
- Main runs inside a chat sort by original creation time ascending, regardless of completion state. Never concatenate active rows ahead of history. Each main is followed by its descendant block; sibling children sort by creation time, not percentage or completion. Thus old main → its children → newer main; when the old main has no children, it sits directly above its followup as shown. Children of earlier runs must stay with that run rather than drifting to the newest run.
- Persist an insertion ordinal for equal timestamps and legacy items without createdAt. Assign legacy ordinals once from saved order, then retain them. Do not use updatedAt, note timestamps, or completion order for chronology. No need for a client-supplied run sequence.
- `t3Thread` already supplies chat identity. `isChild` already supplies role. Neither identifies the run that spawned a child. Internal `ProgressItem.id` identifies a stored instance but is generated after the initial request and is not currently exposed by GET. Add optional client-generated `runId` and `parentRunId` correlation metadata, not another chat/group ID. Every agent creates its own runId before its initial notification; children receive their parent's runId. Sequential main followups create new runIds, omit parentRunId, and share t3Thread. They are chronology, not a parent-child relationship.
- Keep existing name-based update/deletion routing in this scope. runId is immutable correlation metadata for one card lifetime, not a replacement key. Stable unique names remain required among active tasks. A new run with a reused name gets a fresh runId after retirement. Retrying a terminal runId must be a no-op, never create a duplicate; conflicting runIds against a still-active name return 409. This extra validation prevents silently attaching a followup's children to the prior run during the 1.25-second completion window.
- Resolve parent references within the same chat. Missing/hidden parents produce an explicitly labeled “Parent not visible” branch container (nonselectable), retaining children. Never guess by the latest main. Legacy `isChild` cards lacking parentRunId go in a “Children · parent unspecified” branch at the end of the chat. They remain visibly children. Do not fabricate parentage from names or timestamps.
- Nested references may be stored, but flatten rendered descendants to one inset level with a “via [parent task]” subtitle; avoid consuming the 350 px width with unlimited nesting. Validate IDs, reject self-parenting/cycles and cross-chat links; unresolved references remain valid for out-of-order arrival and are checked when resolved.

## Lifecycle and keyboard

History visibility remains explicit: completed cards currently visible remain visible and are sorted into their original timeline position. Do not resurrect all 200 saved records whenever a chat receives an update. H still reveals one newest hidden result globally per press, then places it chronologically in its chat, expands the panel, and selects/scrolls to that result. C hides completed results only, leaving active children and placeholder parent context. Relaunch preserves existing hidden-history behavior. Completion effects and sound fire once per task, never per group or recall.

Up/Down and J/K traverse the flattened visible task order, skipping chat headings, rails, and parent placeholders. Preserve selected UUID across reorder, updates, mode transitions, and completing→history; on removal choose the nearest surviving task. D and Shift+D retain their current note-ledger meanings; D expands a condensed completed row and its ledger. M preserves selection and grouping. Enter opens the existing shared chat destination. X, Z, undo, and close buttons apply only to the selected task, with existing name-ban semantics unchanged: no implicit recursive hide or delete. Group headers have no close action. Ensure tooltips and accessibility labels identify chat, main/child role, parent, title, progress, status, and selected state in compact mode. Scroll only when measured stack reaches the available screen height; include rail/header/branch geometry in the current single animation clock. Reduce Motion preserves connections without movement.

## Backward-compatible API/client proposal

Add optional string fields `runId`, `parentRunId` to POST, persisted ProgressItem/history/deletion/closure state, and GET items. Add existing stored `id` and `createdAt` to GET for diagnostics; preserve all current response fields and POST `{ok:true}`. Missing fields decode as nil for legacy saved state and preserve existing values on subsequent updates. New cards never inherit metadata from prior runs. Require `parentRunId` only with isChild true and a runId; allow a legacy child without either. Correcting a child to main clears parentRunId. Parent metadata is immutable within a run; an explicit admin correction path can be a later feature. Validate UUID syntax and bounds; detect invalid graphs without breaking ordinary legacy updates. The app must still bind IPv4 loopback and reject browser origins.

Example initial parent: `{"name":"Design chat grouping","progress":0,"etaSeconds":180,"t3Thread":{"environmentId":"env","threadId":"chat"},"runId":"11111111-1111-4111-8111-111111111111"}`.

Child additionally sends `"isChild":true,"runId":"22222222-2222-4222-8222-222222222222","parentRunId":"11111111-1111-4111-8111-111111111111"` with its own unique name and the SAME chat destination. A followup has a fresh runId, same chat destination, no parentRunId, and isChild omitted/false.

CLI: add `--run-id UUID` and `--parent-run-id UUID`; retain all positional args and `--child`/`--no-child`. Validate the flag combination before transport. Agents pass runId consistently on every update (unavailable-app initial sends may have been skipped); destination and parent metadata should also be repeated or retained in the agent's invocation template. No client-generated implicit IDs per invocation: this script is stateless and that would create a different ID on every update. Old clients still work with chat grouping and honest unspecified-parent children, and old servers ignore unknown optional JSON keys; new-client flags need deploying before skills adopt them.

## Proposed skill amendments (not applied)

1. Keep “one run, one stable unique name” and all best-effort reporting rules. Add “Generate one UUID runId before your initial notification; reuse it on every update. A user followup is a new run in the same chat, not a child.”
2. Parent briefs must include chat destination, project metadata, and parentRunId equal to the parent's own runId. Each child generates its own runId and uses --child --parent-run-id; nested children pass their own runId onward. Never use a provider thread ID or resolved chat ID as a runId.
3. Replace “same thread-group symbol” wording with chronological chat rails and explicit branch ownership. Clarify role vs destination vs run instance. Keep --child mandatory even when parent identity is unavailable; omit parentRunId and show unspecified ownership rather than invent one.
4. Document condensed completed rows, unchanged H/C history visibility, per-task X/Z, D note ledgers, and selection order. Do not require extra progress notifications to maintain ordering.

## Tradeoffs / review points

The rail is easy to read and does not need a finite pool of arbitrary symbols, but headers and connectors add compact height. Summarizing completed rows trades immediate note detail for enough room to keep prior runs above current work. Keeping first-seen group order prevents distracting jumps but can leave active work lower in a long panel. Exact parent references require two optional metadata fields and lifecycle validation; a zero-API-change version can group by chat and mark children, but cannot honestly show which main run owns a child. Do not ship guessed parent connectors as a shortcut.

Design-only artifacts. No app, client, skill, tests, commit, deployment, or preview changes made. Mockup is static and self-contained; full implementation would require grouping/lifecycle/keyboard tests and the repository's required checks.
